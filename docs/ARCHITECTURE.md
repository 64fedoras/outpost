# Outpost architecture

## Processes and data
**Controller** (`outpost controller`, default :8443, HTTPS with a self-signed certificate). Data dir (`/var/lib/outpost/controller` as root on Linux): `admin.json` (PBKDF2 password hash), `secret.key` (encrypts the Claude and Hugging Face keys), `settings.json`, `sessions.json`, `nodes.json`, `tls.crt`/`tls.key`, `tasks/<id>/` (task.json and repo files), `api_tokens.json`, `tls_repin.json`, `projects/<id>/` (see Projects), `models/<name>/` (controller-stored models, now an optional seed), `runtime/<variant>/` (llama.cpp archives), `toolchains/<tool>/` (Go archive pushed to nodes), `releases/<platform>` (uploaded Outpost binaries), `agent/`. A task folder also holds `rounds/<n>/` (previous copies of files each request changed), `images/`, `attachments/`, `shots/` (screenshots) and `artifacts/` (build outputs fetched from a node), beside `task.json`, `repo/` (unless the task is in a project) and `result.zip`.

**Node** (`outpost node`). Data dir: `node.json` (controller URL, certificate fingerprint, node key), `control.json` (token for the local control server), `paused`, `node.lock`, `llama/` (installed llama.cpp builds), `models/`, `toolchains/` (Go installed by the controller), `work/` (job scratch and build outputs held until the controller fetches them, swept at startup), `agent/` (versions of the binary).

**Ports.** Controller 8443 (web UI, API, node WebSocket). Each node 8444 (`transfer/` file server: model copies between nodes and files over 1 MiB for jobs; its own self-signed certificate, pinned by the downloader, access by one-time token; `OUTPOST_PEER_PORT` overrides it; the installer opens it in ufw, firewalld and Windows Firewall). Pool helpers 50052, or the next free port (gatekeeper in front of ggml-rpc-server on loopback). It exists only while a pool is running and only if pooling is enabled in Settings (off by default); the installer never opens it in a firewall.

## Connection and security
A node joins with a one-time code containing the controller URL, its certificate fingerprint and a secret. After joining it keeps a WebSocket to `/v1/node/ws`, pinned to that fingerprint, and sends a hello plus heartbeats (hardware, loaded model, paused flag, running jobs). The controller pushes jobs, settings, model files, runtime installs and updates over the same socket. Exec jobs run commands as the node's service user and are off unless enabled per node.

## Task lifecycle
Statuses: `planning`, `awaiting_answers`, `awaiting_approval`, `running`, `testing`, `fixing`, `queued` (waiting for the project slot), `paused_cap`, `done`, `failed`, `cancelled`, `interrupted` (set for in-flight tasks at controller restart; Resume continues from finished subtasks, and `tasks_autoresume.go` resumes local-planner tasks by itself once a node with a model reconnects). Subtask states: `pending`, `running`, `written`, `reviewing`, `done`, `failed`.
1. A message creates a **round**. The planner (Claude API or a local node) returns either questions or a plan: title, summary, language, setup and test commands, and subtasks with files, dependencies and instructions.
2. The user answers, replies with changes (re-plans) or approves.
3. The dispatch loop (`executeTask`) repeatedly takes ready subtasks and routes each by difficulty tag (`easy`/`normal`/`hard`), model tier and measured speed (`routing.go`; benchmarks run when a model loads). Hard subtasks may also run on spare nodes with a syntax check and a judge (`bestofn.go`). Streamed text is kept in memory (`tasks_live.go`) and sent to the browser by server-sent events. A node call is one inference at a time. The node writes whole files in a `<<<FILE path>>> … <<<END>>>` format.
4. After a subtask, another node reviews it (optional). Steering notes are added to every prompt that starts afterwards.
5. The controller runs the plan's test command on an exec node (files under 1 MiB are sent), then fix rounds run as an agent with tools (`agent.go`: `list_files`, `read_file`, `search`, `write_file`, `run`, `ask_user`; 30 calls and 20 minutes per run); `investigate` subtasks use the same loop read-only. After the tests pass, the plan's build command runs and its `artifacts` are fetched (`node_artifacts.go`, `controller_files.go`). Pages the round wrote are screenshotted and reviewed by a vision-capable planner (`visual.go`). Large projects get an index instead of full contents (`codeindex.go`, `.outpostignore`); project instructions go in every prompt (`instructions.go`); pasted links are fetched (`weblookup.go`). Notifications (`notify.go`) fire on questions, plans, results, caps and offline nodes.
6. A result message lists the files; later messages start a new round on the same files.
Claude spend is metered per call and a cap pauses the task (`paused_cap`).

## Projects
`projects.go`, `projects_git.go`, `attachments.go`. `projects/<id>/project.json` (schema 1; git token and SSH key encrypted with `secret.key`) and `projects/<id>/repo/`, which is a git working tree when the project has a URL. `Task.ProjectID` points a task at its project and `Task.repoDir()` then returns the project's repo; `.git` is skipped by `listRepo`/`zipDir` and refused by `writeRepoFile` and zip extraction. `execTask` wraps `executeTask`: it takes the project's one-slot channel (status `queued` while waiting), and after a `done` round commits and optionally pushes (`exportRound`) and opens a GitHub PR. Old tasks have no `project_id` and need no migration; a task whose project is missing is unfiled on load. Later rows (project instructions, large codebase index) add fields to `Project` and files beside `repo/`.

## Model and runtime management
A model library entry has storage `controller` (downloaded once, kept as an optional seed) or `direct` (each node downloads from Hugging Face). The controller records each file's SHA-256 first (`controller_peers.go`); a node that needs a model copies it from up to 3 online peers that hold it (`node_peer.go`, `transfer/`), verifies every chunk and the whole file, and falls back to Hugging Face or the controller. `model_fit.go` estimates which nodes a model fits. Vision models carry an `mmproj` file passed to llama-server. The controller picks the llama.cpp build from GitHub releases per node (Vulkan, CPU, macOS) and pushes it. A node can run llama-server alone, or lend memory to a pool through ggml-rpc-server, bound to loopback behind a source-IP allow-list gatekeeper (the main node only; refused connections are logged). That is the whole protection: no authentication, no encryption, spoofable on a hostile LAN, so pooling is a trusted-LAN-only experimental feature, off by default (`controller_pooling.go`: `Settings.PoolingEnabled`, upgrade migration, dissolve on disable). The controller never sends `rpc.start` while it is off, and a node that reports it is still lending is told to stop. The long-term fix is roadmap row 24.

## Updates
`controller_ghupdate.go` polls the repo's latest GitHub release every 6 hours (`Settings.GitHubUpdatesOff`, default on), downloads the binaries for the controller and known node platforms, verifies them against `SHA256SUMS` and the embedded build info, and stores them through the same `installRelease` as an upload. `GitHubAutoInstall` then runs `startNodeUpdate` for idle nodes and installs the controller when no task is busy; a rollback sets `GitHubHoldVersion` so the version just left is not re-applied. `OUTPOST_GITHUB_API` redirects it to a stub.

Binaries are uploaded in the web UI per platform; the controller reads each one's version from an embedded `OUTPOST_BUILD_INFO|<version>|` string, serves it to nodes, and keeps the previous build for rollback. On Windows a running exe cannot be replaced, so the node runs under a launcher that starts the newest installed version and hands over to it (0.6.1: a fresh process and a per-data-dir lock). Since 0.7.0 a Windows node installed from an admin shell is the `OutpostNode` service (`service_windows.go`): the service process is only a launcher that runs `outpost node` as a child inside a kill-on-close job object, restarts it on exit code 75 (update), and stops the service on 76 (Quit from the tray). The tray started with `--service` never starts the node itself.

## Hardening (0.7.0)
`controller_auth.go`: per-IP login lockout (in memory), session metadata in `sessions.json.meta`, API tokens (`api_tokens.json`, SHA-256 hashed; `auth` accepts cookie or bearer, `authSession` only the cookie). `controller_tls.go`: the controller serves `c.cert` through `GetCertificate`; a swap sends `node.repin` to connected nodes, waits for `node.repin_ack`, then writes `tls.crt/key` and switches; nodes that missed it are listed in `tls_repin.json` until they reconnect (`outpost repin` on the node). `backup.go`: tar.gz in 1 MiB AES-GCM chunks (final chunk flagged, so truncation is detected), scheduled copies via `backupLoop`.

## Web UI
Vanilla JavaScript single-page app embedded in the binary, no build step: sidebar shell, task thread rendered by keyed items, CSS variables with dark mode, mobile drawer. Talks to a JSON API under `/api/` (state, tasks, messages, answers, approve, models, nodes, tokens, releases, settings) with a session cookie.

## Platforms
Linux amd64 and arm64, macOS amd64 and arm64, Windows amd64, all built with CGO disabled. Linux service via systemd; tray icon via D-Bus StatusNotifierItem (Linux) and Win32 (Windows); none yet for macOS (a per-user LaunchAgent, `install_launchd.go`, starts the node there).

## Repository layout
Everything Go is `package main` in the repository root (one binary), with `transfer/` as the only sub-package. `web/` is embedded with `go:embed`. `bundled/` holds the gzipped libgomp; `vendor/` all dependencies; `winres/` the Windows version info and manifest; `scripts/` the notices and re-vendoring helpers; `build.sh` and `build.ps1` the build scripts (kept at the root because everything refers to them); `testing/` the end-to-end rig; `.github/` CI, release stamping and Dependabot.
